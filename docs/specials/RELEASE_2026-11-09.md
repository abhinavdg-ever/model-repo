# Release 2026-11-09: Windows laptop and VM

What to do on the Windows laptop (Command Prompt) and the Ubuntu VM (bash) to bring them to
today's code.

On the VM: **Postgres stays the database** (`DB_BACKEND=postgres`). The Cosmos key there is
read-only, and every mode that uses Cosmos writes to it. **Chart runs go through Service Bus** (`RUN_MODE=queue`): the API
queues each chart and the `worker` containers run them.

Order: download → push → VM pull → back up → settings → database → restart → check → re-run
charts → utilities. Database: container `postgres-db` on the VM, user `aiuser`, databases
`imaging_outputs` (ours) and `imaging_outputs_client`.

---

## 1. Windows laptop: download from GitHub and copy into Azure DevOps

The full commands, and the `.gitignore` to keep as `C:\work\devops.gitignore` (once), are in
[VM_GUIDE §5.1](VM_GUIDE.md#51-windows-laptop-command-prompt-each-release). In short:

```bat
:: Windows (Command Prompt)
:: 1. github.com/abhinavdg-ever/model-repo -> Code -> Download ZIP, then unpack it
cd /d %USERPROFILE%\Downloads
rmdir /s /q model-repo-main 2>nul
tar -xf model-repo-main.zip

:: 2. Copy into the DevOps folder. /MIR makes it match GitHub (deleted files go too); the
::    /XD folders (git, venvs, weights, logs, chart output, review data, db-utilities input)
::    and .env files are neither copied nor deleted. Full paths: other folders share names.
set SRC=%USERPROFILE%\Downloads\model-repo-main
set DST=C:\work\advantmed-devops
robocopy "%SRC%" "%DST%" /MIR /NFL /NDL /NP /XF .env ._* .DS_Store /XD .git .venv .venv-test node_modules "%SRC%\core-pipeline\models" "%DST%\core-pipeline\models" "%SRC%\core-pipeline\logs" "%DST%\core-pipeline\logs" "%SRC%\core-pipeline\outputs" "%DST%\core-pipeline\outputs" "%SRC%\review-ui\data" "%DST%\review-ui\data" "%SRC%\db-utilities\input" "%DST%\db-utilities\input"

:: 3. The small model files GitHub keeps (heads, configs, READMEs): added, never deleting
::    the big weights already in the DevOps folder.
robocopy "%SRC%\core-pipeline\models" "%DST%\core-pipeline\models" /E /NFL /NDL /NP /XF ._*

:: 4. Your DevOps .gitignore (the GitHub one was just copied over it)
copy /y C:\work\devops.gitignore "%DST%\.gitignore"

:: 5. Push C:\work\advantmed-devops to Azure DevOps as usual
```

robocopy exit codes 0–7 are success (1 = files copied); 8 or more is a failure.

## 4. VM: back up the database (Postgres in Docker)

The database runs in the Docker container **`postgres-db`** on the VM (172.20.4.170:5432):
`imaging_outputs` is ours, `imaging_outputs_client` the client's. The ground-truth copy in §9
replaces rows and the re-run in §8 rewrites verdicts, so back both up first.

```bash
# Ubuntu VM
docker exec postgres-db pg_dump -U postgres -d imaging_outputs -Fc > ~/backup_$(date +%Y%m%d_%H%M).dump
docker exec postgres-db pg_dump -U postgres -d imaging_outputs_client -Fc > ~/backup_client_$(date +%Y%m%d_%H%M).dump
ls -lh ~/backup_*.dump | tail -2                                      # neither should be tiny
```

To look inside: `docker exec -it postgres-db psql -U postgres -d imaging_outputs` (`\q` to leave).

To put a backup back (only if something went wrong):

```bash
docker exec -i postgres-db pg_restore -U postgres -d imaging_outputs --clean --if-exists < ~/backup_<stamp>.dump
```

## 7. VM: restart and check

```bash

cd ~/advantmed-imaging-pipeline/core-pipeline

# expect: db {'configured': 'postgres', 'active': 'postgres', ...}, run_mode queue, the queue reachable

cd ../review-ui

curl -fsS localhost:4000/docs >/dev/null && echo review-ui up

# db-utilities: build its image once (it runs only when you load a file)
cd ../db-utilities

```

## 8. Re-run charts for the new rules

What changed for results: the blank / junk rules (`docs/specials/BLANK_JUNK_LOGIC.md`), the
page-type tie (Progress Note first) and rotation. `skip_ocr: true` re-runs every stage on the
OCR already stored, so **no Doc Intel bill**. The rotation stage still runs; only a page whose
rotation now comes out different is OCR'd again. With `RUN_MODE=queue` the call returns at
once and the workers take the charts one by one.

```bash
# Ubuntu VM (input_path = the Blob folder the charts came from)
curl -X POST localhost:8001/api/charts/batch-run -H 'Content-Type: application/json' \
  -d '{"input_type":"blob","container_name":"imaging-pipeline","input_path":"raw_input/Batch1/Run1",
       "output_path":"Processed/Batch1/Run1","skip_ocr":true}'
```

```bat
:: Windows (Command Prompt), against the VM
curl -X POST http://172.20.4.170:8001/api/charts/batch-run -H "Content-Type: application/json" -d "{\"input_type\":\"blob\",\"container_name\":\"imaging-pipeline\",\"input_path\":\"raw_input/Batch1/Run1\",\"output_path\":\"Processed/Batch1/Run1\",\"skip_ocr\":true}"
```

Add `"chart_list": ["<chart>", ...]` to re-run only some charts. Progress: the call answers
with a run id per chart; `curl -s localhost:8001/api/runs/<run id>` (queued / running / done),
`curl -s localhost:8001/api/charts/by-name/<chart>`, and `docker compose logs -f worker`.

## 9. The two utilities (from the Windows laptop)

The laptop reaches the database at 172.20.4.170:5432, so both run there from the
core-pipeline venv (`cd core-pipeline && .venv\Scripts\activate.bat`). `DATABASE_URL` set in
the window wins over the one in `.env`. Put your password where it says `<password>`.

```bat
:: Windows (Command Prompt), in the DevOps folder (or the unzipped model-repo-main)
cd /d C:\work\advantmed-devops\core-pipeline
.venv\Scripts\activate.bat
set "DATABASE_URL=postgresql+psycopg://aiuser:<password>@172.20.4.170:5432/imaging_outputs"
set "CLIENT_DATABASE_URL=postgresql+psycopg://aiuser:<password>@172.20.4.170:5432/imaging_outputs_client"

:: Mark charts "Special" (History and Accuracy filter by tag)
python ..\utilities\tag_chart.py 52743839_44976074 --tag Special
python ..\utilities\tag_chart.py --from-file charts.txt --tag Special
python ..\utilities\tag_chart.py --list-tags

:: The client's ground truth into ours
python ..\utilities\pull_client_ground_truth.py
python ..\utilities\pull_client_ground_truth.py --apply
python ..\utilities\pull_client_ground_truth.py --list-backups
python ..\utilities\pull_client_ground_truth.py --restore gt_backup_<stamp>
```

The first `pull_client_ground_truth.py` is a dry run: rows per table, ours vs the client's.
`--apply` backs ours up (schema `gt_backup_<stamp>` + CSVs in `utilities\output\`) and then
copies. No venv on the laptop yet: `py -3.12 -m venv .venv`, activate, then
`pip install -r requirements-basic.txt`.

The same from the VM:

```bash
# Ubuntu VM
cd ~/advantmed-imaging-pipeline/core-pipeline && source .venv/bin/activate
export DATABASE_URL='postgresql+psycopg://aiuser:<password>@172.20.4.170:5432/imaging_outputs'
export CLIENT_DATABASE_URL='postgresql+psycopg://aiuser:<password>@172.20.4.170:5432/imaging_outputs_client'
python ../utilities/tag_chart.py 52743839_44976074 --tag Special
python ../utilities/pull_client_ground_truth.py              # dry run
python ../utilities/pull_client_ground_truth.py --apply
```

Check it in the database:

```bash
docker exec postgres-db psql -U postgres -d imaging_outputs -c "SELECT count(*) AS pages, count(DISTINCT chart_name) AS charts FROM page_ground_truth;"
```

Then review-ui → Accuracy View → **Refresh**, and **Download Page Level Accuracy** for the
page-by-page Match / No Match file.
